# Flight Sim Builder

ブラウザ製の3D飛行機シミュレーター。現在は **機体設定画面（Builder）** に加えて、
**環境プレビュー**（3,000km四方の世界／空・雲・昼夜サイクル／天候／海と陸／気候帯／
川と湖／植生／国・都市・空港）と、**Builderで作った機体を実際に飛ばす飛行モード**
（飛行物理・操縦・追尾/コックピット視点・計器）まで実装済み。

Three.js (r128, jsDelivr CDN) + vanilla JS。ビルドツールなし、ローカルサーバーで
`index.html`（Builder）または `flight.html`（環境プレビュー）を開けば動く。

---

## 公開（GitHub Pages）

ビルド不要の静的サイトなので、リポジトリをそのままGitHub Pagesで公開できる。

1. リポジトリの Settings → Pages
2. Source: `Deploy from a branch`
3. Branch: `main` / フォルダ: `/ (root)` → Save

公開後のURL:

- Builder: `https://<ユーザー名>.github.io/susuru-airplane-sim/`
- 環境プレビュー: `https://<ユーザー名>.github.io/susuru-airplane-sim/flight.html`

前提として、HTML/JSの参照はすべて相対パスにしてある（`/susuru-airplane-sim/` のような
サブパス配信でも壊れないようにするため）。Three.jsはjsDelivrのhttps配信なので
混在コンテンツエラーは出ず、IndexedDBへの保存もhttpsオリジンなので通常どおり動く。
ルートの `.nojekyll` はJekyll処理をスキップさせるためのもの。

## 設計上の重要な決めごと

### 座標系と親子関係
- パーツのギズモ・重心ギズモは **`State.model.root`（機体モデル）の子** として追加する。
  これにより機体の向き・大きさを変えるとパーツも自動追従する（Three.jsの階層変換に任せる）。
- したがって `part.position` は **機体モデルのローカル座標**。
- モデル本体のメッシュには読込時に `userData.isModelMeshRoot = true` を付け、
  パーツのギズモと区別できるようにしてある（原点調整でモデルだけを動かすため）。

### 重心を主翼から決める
- 「主翼から決定」（`setCgFromWings`）は **X・Y・Zの3軸とも** 動かす。
  X＝左右主翼の中間（対称の中心線）、Z＝主翼の**空力中心**の前後位置、Y＝主翼の面の高さ。
- Zに使うのはパーツの原点ではなく、4頂点から出した**前縁から1/4翼弦**を面積で
  重み付けした点。パーツの原点は翼のどこにあってもよい（形の基準でしかない）ので、
  原点に重心を合わせると、実際に揚力がかかる場所と何メートルもずれることがある。
  ずれたぶんは飛ばした瞬間から機首を上げ下げする力になり、釣り合う相手がいない。
- 以前はXしか動かさなかった。左右の対称は取れても前後が合わないので、
  「主翼と重心は合っているのに勝手に機首上げする」機体ができていた。

### 垂直離着陸用エンジンの釣り合い（Builder側）
- 上向きのエンジン（`spinAxis='y'`）を選ぶと、インスペクターに**推力の中心が重心から
  どれだけずれているか**が出る。左右はミラー複製で揃うが、前後まで重心に合わせるのは
  手作業ではまず無理なので、置きながら数字で見えるようにしてある。
- 「推力を釣り合わせる」（`balanceVtolThrust`）は**位置を動かさず、各エンジンの推力を
  解き直して**中心を重心へ揃える。エンジンの位置はモデルのナセルに縛られていて動かせない
  ことが多いので、動かせるほうの推力で合わせる。
- 解きかたは等式制約つき最小二乗。守るのは「前後のモーメント=0／左右のモーメント=0／
  合計推力は今のまま」の3つで、倍率の取りかたは無数にあるから
  **いまの配分からの変化がいちばん小さい**ものを選ぶ（`u = Aᵀ(AAᵀ)⁻¹b`）。
  前後2群だけの機体なら、答えは素直に腕の長さの逆比になる。
- 重心の前後どちらかにしかエンジンが無ければ、推力をどういじっても釣り合わない。
  そういう配置では**書き換えずに断る**（無理に触ると出力が0以下になる）。
- 飛行側の `applyVtolTrim` は、釣り合っていない機体でも飛べるように強いほうを絞る。
  Builderで揃えておけば絞るものが無くなり、定格の推力を全部使える
  （Thunderbird2の配置では 89% → 100%）。

### ピッチの釣り合い（Builder側）
- 「主翼から決定」は重心を主翼の空力中心へ**ぴったり**合わせる。これは水平尾翼を
  持つふつうの機体には正しいが、水平尾翼を持たずエルロン（エレボン）だけで飛ばす
  機体（デルタ翼など）だと、舵を切っても力の掛かる点が重心の真上（腕=0）になり、
  **舵がまったく効かなくなる**——実際にユーザーの機体（Concorde型）でこれが起き、
  原因の分からないまま「うまく飛べない」という報告になった
  （`js/env/10-flight.js` の `solveLevelTrim` が `no_elevator` という理由を返すように
  なっていて、飛行側の性能診断にはエラーとして出る）。
- 「空力バランスを整える」（`js/05e-pitch-balance.js` の `balancePitchTrim`）はこれを
  2段で直す。**重心とエンジンの角度、どちらもBuilderは飛行モデル（09-aircraft.js）を
  読み込んでいないので、同じ計算をここで独立に行う**：
  1. 重心を、主翼（＋水平尾翼があればそれも面積で重み付けして）の中立点から、
     ふつうの静安定（翼弦の10%）ぶん前へ離す。「前」は主翼自身の翼弦の向きから
     決めるので、機体がどちらを向いて作られていても正しく前へ動く
     （09-aircraft.js の `acOrientationFix` と同じ考え方）。
  2. それでも残るエンジン推力のずれ（推力線が重心を通らず、出力を上げるほど
     機首を振る力になる）は、**エンジンの角度そのものを傾けて**打ち消す。
     角度は当てずっぽうではなく、実際にモーメントの式へ通して挟み撃ちで解く
     （VTOLバランスの `trimBisect` と同じ考え方）。機体の前後軸をヨーだけ揃える
     クォータニオンを作り、その中で `r × F` を計算しているので、09-aircraft.js
     側の実際の物理と同じ答えになる。
- **この機能のために、エンジンの向きの物理を直した**。以前は `spinAxis`
  （x/y/z の決め打ち）だけで推力の向きを決めていて、Builderでエンジンパーツを
  傾けて取り付けても（見た目は傾くのに）推力はまっすぐ出続けていた。ここは
  パーツ自身の回転を推力方向にも掛けるようにして直した——**ただし
  `modelTransform` の回転は掛けない**。`spinAxis` は「Builderの画面に
  常に映っている向き」（＝ modelTransform を適用したあとの見た目）を指す約束で、
  ユーザーはその画面を見ながら「前」「上」「横」を選ぶ。一度は
  `modelTransform` の回転も掛けるよう直したが、それは前後逆さに作られた
  モデルを `modelTransform` で直した機体（747のケースなど）で
  **翼は正しく機首(-Z)を向くのにエンジンの推力だけ後ろ向きになる**という、
  直したはずが直った状態を壊す結果になった——qFix（主翼の向きから来る、
  機体ぜんぶへの最終補正）だけで既に辻褄が合っていたところへ、
  `modelTransform` の回転をもう一段重ねてしまっていた。
- 静安定10%は「解けない機体」への保険ではなく実機の目安（ふつう5〜20%）。
  合わせるとエレベーターが利くだけでなく、勝手にうねる度合いも収まる。

### エンジン出力の自動設定（Builder側）
- エンジンを置いても、その推力が「設定した最高速度まで出せるか」「垂直に浮けるか」は
  自分で計算しないと分からない。機体設定パネル（重量・最高速度のすぐ下）に
  `js/05f-engine-power.js` の機能を出し、逆算した推力をその場で書き戻せるようにした。
- 「最高速度に必要な出力へ自動設定」（`applyEngineSpeedTarget`）は、09-aircraft.js の
  抗力式（誘導抗力＋胴体抗力＋尾翼の有害抗力）と `propFactor`（速度が上がるほど
  推力が落ちる効き）を**Builder側で独立に再現**して、設定した最高速度で釣り合う
  合計推力を逆算する。前へ進むエンジンが複数あれば、**いまの推力の比率を保ったまま**
  全体の大きさだけを解き直す（全部ゼロなら均等割り）。
  - 逆算した値は控えめに見積もった抗力の35%増し（`EP_SPEED_THRUST_MARGIN`）。
    釣り合いぎりぎりだと最高速度に漸近するだけで実際には届かないうえ、
    Builder側の簡略式は主翼の面積・アスペクト比だけから見積もっていて、
    尾翼が水平飛行のトリムで作る誘導抗力など、実際の飛行モデル
    （`10-flight.js` の `accumulateAeroForces`、翼1枚ずつ積み上げて計算する）が
    出す値より2〜3割ほど小さく出る——これは推測ではなく、内蔵の練習機を使って
    `solveLevelTrim` の実際のスロットル要求値と突き合わせて測った差。
- 「垂直離陸に必要な出力へ自動設定」（`applyVtolSpeedTarget`）は
  `js/05d-vtol-balance.js` の `vtolBalanceReport` が出す `usableRatio`
  （前後バランスで絞られたあと、実際に使える推力の割合）を使い、**絞られるぶんを
  見込んで多めに**積む。目標は使える推力で重量の130%（`EP_VTOL_TWR_TARGET`）——
  100%はぎりぎり浮くだけで上昇・姿勢制御の余力が無い。
- どちらも、対象のエンジンが1基も無い・向きが違う（前へ進むエンジンが横や上しか
  向いていない等）・主翼が無く最高速度の抗力を見積もれない、といった場合は
  **書き換えずに断る**（他の自動化ツールと同じ流儀）。
- 通常エンジン・垂直エンジンそれぞれに、一括で倍率をかけるだけの操作
  （`epScaleEngines`）も同じパネルに置いた。自動設定とは別物で、
  「もう少し出力に余裕を持たせたい／絞りたい」というときに、比率はそのまま
  全体を底上げ・底下げする。倍率は0より大きい数のみ受け付ける。
- **保存済み設定を読み込んだ直後、ボタンが出ないことがあった**
  （`applyConfigDataToCurrentModel`）。このパネルは `State.parts` を見て
  エンジンの有無を判断するが、パーツを読み込む `rebuildPartsFromSaved` より
  **前**にパネルを描画していたため、読み込んだ直後は毎回「パーツがまだ空の
  状態」で描かれ、その後パーツが増えても再描画されなかった（GLBだけ読んで
  パーツが本当に無い場合は正しく出ない、という自然な見た目だったため気付き
  にくかった）。パーツ・重心を反映し終えたあとにパネルを描画するよう順序を
  入れ替えて直した。

### 原点調整
- `centerModelOnAxis(axis)` の `axis` は **画面上の見た目の軸（ワールド座標系）**。
  `root.rotation` が回っていても見た目通りに動くよう、ワールドの移動量を
  rootの回転・スケールの逆変換でローカルに直してからメッシュへ適用している。
- 移動量は `State.model.meshOffset` に累計され、保存/復元される。

### 翼の4頂点
- `props.corners` は `rootLeading / rootTrailing / tipLeading / tipTrailing` の4点。
  パーツのpositionを基準としたローカルオフセット。
- 翼のジオメトリはこの4点から動的生成する（`buildWingGeometryFromCorners`）。
  厚み方向は水平翼ならY、垂直尾翼ならX。
- 4点の中心が **揚力中心** として扱われる（主翼の場合）。
- `wingPointAt(corners, spanS, chordT)` でバイリニア補間により翼上の任意の点を取れる。
  可動翼面の「後縁1/4に自動配置」はこれを使い `chordT=0.875` で計算している。

### 着陸脚
- `props.joints[]`（関節：回転軸＋角度範囲）と `props.struts[]`（伸縮節：長さ範囲）を
  交互にチェーン状に連結した階層として3D構築する。
- 伸縮節は **-Y方向（下向き）** に伸びる。次のセグメントは伸縮節の子 `endAnchor` にぶら下がる
  （これが無いと伸縮しても先端の位置が動かない）。
- `deployState`（0=格納〜1=展開）で全関節・全伸縮節を線形補間してプレビューする。
- `fitGearToGround()` はワールド座標で先端位置を測り、地面(Y=0)に届くよう
  最後の伸縮節の `maxLength` を逆算する。機体の回転・拡縮も考慮済み。

### 環境（空・雲・昼夜サイクル）
- Builderのシーン（`State`）とは完全に独立した、`flight.html` / `EnvState` 専用のシーン。
  将来、飛行シーン本体を作る際にこのシーンへ機体・物理・操縦を足していく想定。
- 空は `THREE.Sky`（Preethamの大気散乱モデル。CDN配布の `examples/js/objects/Sky.js`）を使用。
  太陽の単位方向ベクトル（`sunPosition`）だけをシェーダーに渡せば、朝焼け〜正午〜夕焼けの
  空の色がなめらかに変化する。
- 時刻は `EnvState.time.hours`（0〜24の小数）で管理し、`EnvState.time.cycleMinutes`
  （デフォルト15分）で「24時間ぶんを何分で一周させるか」を調整する。
  `computeSunDirection(hours)` が簡易的な正弦モデルで仰角・方位角を出し、
  太陽・月・光源・霧・星の見た目をすべてそこから一括更新する（`updateSkyForSunDirection`）。
- 太陽の仰角がおよそ-6°〜10°の範囲を「市民薄明」の目安として日中/夜間の度合い
  （`dayFactor`）を滑らかに切り替え、光源の強さ・色（朝夕はオレンジ寄り）・
  星のフェードイン・月明かりの点灯に反映している。
- 雲は外部画像を使わず、キャンバスで生成した柔らかい円形テクスチャをスプライトとして
  複数まとめ、積雲1個分の「塊（クラスタ）」を作る。あらかじめ最大数のクラスタを
  用意しておき、雲量スライダーでは表示数を切り替えるだけ（ジオメトリの作り直しはしない）。
  風速・風向で塊の位置を進め、**カメラを中心に**ラップさせるので、どこまで飛んでも
  雲が周囲に居続ける（原点まわりの数kmだけに置くと、空に浮いた板に見えてしまう）。
- 「高度による空の色の変化」は `EnvState.env.previewAltitudeM` で決まる。高いほど霞
  （霧の密度）が減り、空・霧の色が濃い青へ寄る。飛行中は**機体の実高度がそのまま入る**
  （もともとスライダーだったのは機体が無かったため。スライダーは飛行していないときの代用）。

### 天候
天候は「場所と時間で移り変わる気象の場」と「その土地の気候」から作る。
3,000km四方の世界なので、天気を1つのスライダーで決めてしまうと世界が狭く感じられる。

- **気象の場**（`worldWeatherFieldAt(x, z, 時刻)`、`js/env/03b-world.js`）が
  「湿り」「荒れ」「霧」の3つを返す。fBmを時刻ぶんずらして評価しているだけなので、
  低気圧が風下へ流れていくように見える（1系統およそ240km、時速34kmで移動）。
  地形と同じく種から決まるので、同じ場所・同じ時刻ならいつ開いても同じ天気になる。
- **気候**（気温・乾燥）を掛けて、乾いた土地では雨雲が来ても降りにくく、
  寒い土地では雨ではなく雪にする。
- この2つを `deriveWeather()` が受け取り、雲量・雲底・視程・降水量・風速・
  日射の減り方といった「見え方」に落とす。**自動でも手動でもここを通る**ので、
  プリセットを選んだときと自動のときで作りが食い違わない。
- ただし**気候を掛けるのは「自動」のときだけ**。「雨」を選んだのに砂漠だから降らない、
  では操作に応えていない。プリセットと手動は選んだとおりの天気を出す。
- 目標値へは指数平滑（時定数6秒）で寄せる。プリセットを切り替えても、
  飛んで天気が変わっても、パッとは切り替わらない。
- 見た目の内訳：
  - **曇り空の天井**（`cloudDeck`）＝雲底に張る同心円メッシュ。模様は明るさに入れて
    不透明度は一定にしてある。模様を不透明度に入れると、べったり曇っているはずの空に
    いつも穴が空き、雲の上に出たとき床が透けて地面が見えてしまう。
  - **降水**＝カメラを中心とした150m四方の箱に粒を置き、外へ出たら反対側から入れ直す。
    カメラの移動ぶんを引いているので、飛ぶと粒が後ろへ流れる。雨は速度方向の線分、
    雪は点。雲の天井より上へ出ると降水は消える。
  - **視程**→霧の密度。`FogExp2` は `1-exp(-(距離*密度)^2)` なので、
    「視程の4割の距離で半分霞む」で合わせて `密度 = 2.1 / 視程`。視程そのもので
    合わせると近くがほとんど霞まず、霧の中に居る感じにならない。
  - **空の霞**（`skyHaze`）＝カメラを囲む半径9kmの球。`THREE.Sky` は自前のシェーダーなので
    `FogExp2` が効かず、そのままだと視程700mの濃霧でも青空が見えてしまう。
    深度テストは有効のまま半透明の先頭（`renderOrder -1`）に描くので、
    手前の地形や滑走路は普通に見えたまま、空と遠景の雲だけが霞に沈む。
    色は自分で塗らず**霧に塗らせる**（`fog: true`）。トーンマッピングを通した色と
    シェーダーが霧として書き込む色は一致せず、自前で塗ると霞の球だけ違う灰色になる。
  - **雷**は荒れているときだけ `hemiLight` を一瞬持ち上げ、霧の色も白く振る。
- **気象レーダー**（ミニマップに重ねる。既定はオフ）。本物と同じく映すのは降水だけで、
  雲や霧は映らない。弱い雨は青、強くなるほど緑→黄→橙→赤。雪は寒色、雷のところは紫。
  凡例はいま映っているものに合わせて「雨／雪／雨雪」と出し分ける。
  天候を固定しているときは全域が同じ天気になるので、その旨を地図の隅に書く。
  - 重いのは標高（＝気温）なので、**地図を焼くときの標高をそのまま気候として控えておく**。
    時間で変わるのは気象の場だけなので、塗り直すのはそちらだけで済む（1面あたり約1.2ms、
    0.3秒に1回）。`deriveWeather(…, { climateAt })` はそのための入口。
  - 解像度は地図の4画素にひとつ（58×58）。粗いまま拡大して重ねている。
- 風速は既定で天候に任せる（`env.windFromWeather`）。荒れているほど強く、突風も乗る。
  風速スライダーを動かすとチェックが外れて手動に切り替わる。風向はいつでも手動。
- **天気の内訳は `tools/verify-world.js` が陸と海に分けて毎回出す**。しきい値は目分量ではなく、
  世界ぜんぶを何時刻ぶんか分類して決めた（陸は快晴39/晴れ26/曇り14/雨系10/雪系4/霧7%、
  海はそれより湿って快晴33/晴れ23/曇り15/雨系14/雪系9/霧6%程度）。
  **陸だけ見て決めないこと**：陸の雨は乾燥で抑えられるが海では抑えが効かないので、
  陸に合わせると海の上だけ土砂降りだらけになる（レーダーを入れて初めて気付いた）。
  同じ検証で「強い雨がまれであること」「海のほうが陸より降っていること」
  「1,500km離れれば天気が変わる」「プリセットが名前どおりの天気になる」も見ている。
- 未実装：季節、積雪の堆積（雪は降るが地面に積もらない）、雲の中に入ったときの視界。
- 大気散乱シェーダーは明るさ1.0を超える値を返すため、レンダラーに
  ACESフィルミックのトーンマッピング（露出0.6）をかけている。これが無いと
  空の上部が白飛びし、地表も露出オーバーになる（Three.jsのSky公式サンプルと同じ設定）。
- マテリアルの色は `outputEncoding=sRGB` で中間色が持ち上がるぶんを見越して、
  見た目より一段暗い値を指定している（そのままだとアスファルトが白っぽく飛ぶ）。

### 世界（マップ）
- **3,000km四方の固定マップ**。ワールドの **-Zが北・+Xが東**、単位はすべてメートル。
- `js/env/03b-world.js` の **`worldHeightAt(x, z)` が世界の唯一の正**。
  地形メッシュ・海・川・湖・植生・都市・空港の標高・ミニマップは全部これを見て作られる。
- 地形も地名も **乱数ではなくハッシュから作る**ので、何度読み込んでもまったく同じ世界になる。
  だから「マップ上の固定の空港・都市」が成立し、保存すべきものが「変更ぶん」だけで済む。
- 大陸は楕円のブロブ＋ドメインワープ＋海岸線ノイズ。山脈は名前付きの楕円＋尾根状ノイズ。
- 国は手で10か国置き、その中の都市・空港は手続き的に生成する。
  地名は国ごとの音節表（nordic / imperial / desert / oriental / latin / island …）から
  ラテン表記とカタカナ表記を対で作る。空港コードは「国の2文字＋都市名の2文字」。
- **数百個の地物との距離判定を高さ関数から毎回行うのは無理**なので、
  影響範囲を格子に登録する空間インデックス（`makeWorldGrid`）を通す。
- このファイルは **THREE.jsに一切依存しない**ので、Nodeからそのまま読める。
  `node tools/verify-world.js` で街が沈んでいないか・滑走路が平らか・川が海に届くかを
  ブラウザ無しで検証できる。**地形のパラメータを触ったら必ず流すこと。**

### 世界を広げても重くならない仕組み
- 地形・都市・空港・水面・植生は、すべて **カメラの周りだけを作っては捨てる**。
  実体化される量はカメラの周りで一定なので、`WORLD_SIZE` を大きくしても
  メモリと描画の負荷は変わらない（増えるのは都市・空港の生成量だけ）。

  | もの | 実体化する半径 | 単位 |
  |---|---|---|
  | 地形タイル | 300km | 30km角・分割数はLODで96〜10 |
  | 空港 | 120km | 選択中の空港は距離に関わらず建てる |
  | 都市 | 90km | 1都市＝建物1メッシュ＋夜景1Points |
  | 川・湖 | 130km | |
  | 樹木 | 1.2km | 400m角タイル・対地高度2,500mを超えると消す |
  | 地名ラベル | 種類ごと | スプライトは近づいた時に作ってキャッシュ |

### 遠方の座標精度（ハマりどころ）
- タイル・都市・空港・水面の頂点は **その地物の原点からのローカル座標** で持ち、
  ワールド上の位置は `mesh.position` に入れる。
- 頂点をワールド座標のまま持つと、原点から1,000km以上離れた場所で
  **float32の精度が1m近くまで落ち**、滑走路の路面標識のような細かい造作が壊れる。
- three.js は `modelViewMatrix` を倍精度で組んでから float32 に落とすので、
  この持ち方なら3,000km先でも精度が保たれる（実測：1,253km先で頂点は最大1,294m）。

### 地形メッシュの上の高さ（ハマりどころ）
- 木や建物を `worldHeightAt()` の値に置くと、**宙に浮いたり地面に埋まったりする**。
  地形メッシュは格子点の間を三角形で結んだ折れ面なので、格子点以外では
  真の高さと数十mずれるため。
- `terrainSurfaceHeightAt()`（`03c-terrain.js`）が地形と同じ格子・同じ三角形分割で
  補間した高さを返す。地面に載せたいものは必ずこれを使う。

### 気候帯
- 緯度（-Zが北＝寒い）・内陸度・標高から **気温** と **乾燥度** を出す。
- 気温が **森林限界と雪線** を決めるので、北へ行くほど低い標高から岩と雪になる。
- 乾燥度が草原→ステップ→砂漠への色の寄せ方と、樹木の密度を決める。
- 係数は `tools/verify-world.js` の「陸の気候」の出方を見て決めた
  （温帯20/熱帯15/寒帯20/半乾燥24/砂漠14/雪氷8%）。
  **内陸度だけで乾燥を決めると大陸の中身が全部砂漠になる**ので、
  主役はノイズ（どこに乾燥帯があるか）で、内陸度はそれを底上げするだけにしてある。

### 地形と海
- 地形は30km角のタイル。カメラからの距離で分割数を96〜10に切り替える。
- LODが違うタイルの境目にできる隙間は、縁を1,200m下へ垂らす **スカート** で裏から塞ぐ。
- 法線をタイル境界でも滑らかにつなぐため、高さは外側に1リング広くサンプルして
  中央差分を取っている（端で片側差分にすると継ぎ目に折れ線が出る）。
- 気候は数百km単位でしか変わらないので、頂点ごとではなくタイル内の粗い格子で拾って補間する。
- 海は **y=0に置いた半透明の水面**。浅瀬の水色は海面ではなく海底（地形メッシュ）の色で出す。
  こうすると砂浜〜浅瀬〜深海が地形の解像度そのままで出るので、海面側にシェーダーが要らない。
- 空ドーム・太陽・月・星は **カメラに追従するGroup** に入れてある。原点固定のままだと、
  少し飛んだだけで空ドームの外に出てしまい、空が板になって太陽を後ろに置き去りにする。

### 川と湖
- **川は河口から上流へ遡って引く。** 源流から下らせる素直な実装だと、
  大陸の内側にいくらでもある窪地にはまり、海まで届いたのは68本中1本だけだった
  （尾根ノイズが大陸規模の傾きより強いため）。
  逆に海岸から「いまの高さより高い隣のうち、いちばん低いところ」を選び続けると
  谷底を遡ることになり、行き止まりは山頂にしかない。最後に順序を反転する。
- 経路探索は「強くならした地形」の上で行う（素の地形だと数kmで穴にはまる）。
  8方向にしか進めないので折れ線は45°刻みになる。Chaikinを2回かけて角を落とす。
- 川床は上流から下流へ単調に下がり、かつその場の地形より上には出さない。
  尾根を越えるところだけ深く、谷ではほぼ地形なりの谷が刻まれる。
- 湖は内陸の平らな窪地を椀状に掘り、水面は掘る前の地面の高さに置く。
  岸は「中心から外へ地形を辿って水面の高さに達したところ」を72方向で拾うので、
  掘り方と描き方が同じ判定を見ることになり、丘に食い込む形もそのまま出る。
- **刻む順番**：素の地形 → 街の均し → 川と湖 → 空港の均し。
  水は min() で下げるだけなので街を水没させず、谷は街の中でも残る。
  空港の均しは最後なので滑走路の平面が必ず勝つ（川の経路も空港を避けて引く）。
- 川床・水面・岸の幅は **世界側の定数から導く**形に一本化してある。
  地形の刻み方と水面の張り方が食い違うと、水が地面に埋まる／地面が水から出る。
- 谷を急に刻むと幅が1km程度になり、数十km先の粗いLODでは谷が再現されず
  地形が水面を突き抜けて川がちぎれる。谷は広く浅くし、水面にも路面標識と同じ
  デカール用の深度バイアスをかけている。

### 植生
- 木は手前1.2kmだけ。400m角のタイルごとに1つの `InstancedMesh` にする。
  生える場所・大きさ・向きは座標のハッシュから決まるので、戻れば同じ森になる。
- 木1本は円錐の側面5面だけ（幹は数百m先で見えない）。
- **木を広く薄く撒くと「森」ではなく「点在する棒」に見える。**
  手前を森として成立する密度（16m間隔）で埋め、遠景は地表色の森に任せる方がよい。
- 上空からは半径のふちが地面に円として見えるので、対地高度2,500mを超えたら消す。
- `InstancedMesh` の視錐台カリングは **共有しているジオメトリの境界球** で判定される。
  ここでは木1本ぶん（半径1m）の球なので、放っておくとタイルまるごと消える。
  木は手前だけなので判定を切ってある。

### 飛行
Builderで作った機体を、その定義のまま飛ばす。翼の4頂点・エンジンの推力・重心・重量が
そのまま空力の入力になるので、Builder側で機体を組み替えると飛び方も変わる。

- **翼1枚ごとに空力を計算する**（`js/env/10-flight.js`）。機体全体に揚力の式を1本当てる
  のではなく、翼・水平尾翼・垂直尾翼のそれぞれで迎角→揚力係数→力を出して足し合わせる。
  手間はかかるが、欲しい挙動がほとんど勝手に出てくる：
  - 尾翼が重心から離れているのでピッチもヨーも自然に安定する
  - 回転すると尾翼の局所的な気流（ω×r）が変わるので**減衰も勝手に効く**
  - 片翼だけ失速すればそちら側から落ちる
  - 上反角がついていれば横滑りで勝手に起き上がる
  安定微係数の表を書くより、機体を組み替えたときに素直に追従する。
- 揚力係数は失速角（15°）までは薄翼理論の直線（2πα）、超えたら平板（2 sinα cosα）へ
  なめらかに渡す。失速してもぬるりと揚力が残り、機首を下げれば素直に回復する。
- **力をかける点は前縁から1/4**（空力中心）。4頂点の中心＝翼弦の中央にかけると、
  空力中心が1/4翼弦ぶん後ろにずれてその分だけ機体が余計に安定する。実際そうなっていて、
  エレベーターを一杯に引いても迎角が2°までしか上がらない機体になっていた。
- **取付角は二重に数えない**。翼の `fwd`（前向き）はその翼の4頂点から作るので、
  取付角はこの時点ですでに入っている。ここへさらに `incidenceRad` を足すと
  2°で付けた主翼が4°で飛ぶ。重心の前にある主翼ならそのぶん機首上げの力が出て、
  手を離すと勝手に上を向く機体になる。`incidenceRad` は表示用の数字として持つだけ。
- **舵は「親の翼をまるごとひねる」扱いなので、翼のどれだけを占めるかを掛ける**
  （`CONTROL_SPAN_FRACTION`）。エレベーターとラダーは尾翼のほぼ全幅に付くのでそのままでいいが、
  **エルロンは外翼の一部にしか付かない**。同じ扱いにすると「エルロンを20°切る＝主翼をまるごと
  11°ひねる」ことになり、内蔵の練習機が毎秒310°（実機の6倍）で転がっていた。
  外翼ぶんの0.20を掛けて、実機並みの毎秒60〜70°になる。
- **誘導抗力のアスペクト比は左右をつないだ翼全体で測る**。片翼だけで span²/面積 を出すと
  実際の半分になり、誘導抗力が倍になる。
- **フラップはキャンバーの増加として扱う**。迎角をずらすだけにすると失速角も同じだけ
  前倒しになって最大揚力が増えず、フラップを下ろすほど失速が早まる逆の機体になる。
  失速の判定からフラップぶんを外して、揚力の曲線ごと持ち上げている。
- **機体の前後は決め打ちにしない**。Builderの既定値では前縁が-Z側だが、+Zを向いた
  モデルに合わせて頂点を置いた機体も作れる。主翼の翼弦から機首の向きを読み取り、
  標準の姿勢（機首-Z・上+Y・右+X）へ直す補正クォータニオンを作って、
  以降の物理はその1つの座標系だけを見る。
- **接地点は脚の鎖をたどって実際に求める**。Builderの脚は「関節→伸縮節→関節→…」を
  交互につないだ形で、伸縮節は必ず-Y方向へ伸びる。脚を出しきった状態（deployState=1）で
  この鎖を組み立てた先端が車輪の位置になる。ここを「モデル座標のY=0が接地面」と
  決め打ちすると、Builderで「地面にフィット」を押していない機体が地面に埋もれる。
  脚を置いていない機体は境界から三脚を推定する。
- **どの車輪が操向輪かは、名前ではなく配置で決める**。`gearPosition` は人が付ける札なので、
  後ろの車輪に「前脚」と付いていることがある。左右に開いた対を主脚（ブレーキあり）、
  中心線上の1輪を操向輪と見なせば、札が何であっても正しく振る舞う。
- **パーツの回転は「度」で保存されている**（Builderの `applyPartToGizmo` が degToRad してから
  gizmo に入れている）。ラジアンとして読むと180が28回転になり、脚も翼も明後日を向く。
  ただし**機体まるごとの回転（`modelTransform.rotation`）だけはラジアン**——`root.rotation`
  をそのまま書き出しているため。同じつもりで読むと壊れる。
- **機体まるごとの向き・大きさ（`modelTransform`）は、メッシュとパーツの両方に掛ける**。
  Builderでは `State.model.root` の子にメッシュもパーツもぶら下がっているので、機体を回すと
  両方が一緒に回る。飛行側でメッシュにだけ掛けていたせいで、GLBの前後が逆で180°回してある
  機体は「パーツ（＝物理）は反転しているのに、見た目だけ元の向き」になっていた。
  見た目の階層も Builder と同じ形（`modelXform` が root の役）にしてある。
  拡大縮小も同じで、2倍にすれば翼幅も2倍・翼面積は4倍として飛ぶ。
- **エンジンの推力の向きは `spinAxis`** から決める。z＝前向き、y＝上向き（垂直離陸用の
  リフトエンジン）、x＝横向き。ここを前向き固定にすると、垂直離陸用の推力が
  前へ押してしまう。
- **上を向いたエンジンは別のレバーで出す**（`controls.vtolThrottle`、キーは X／Z）。
  前へ進むエンジンと同じレバーにすると、浮かせようとしただけで前へ走り出し、
  ホバリングも垂直着陸もできない。
- **垂直離陸中は姿勢制御ノズルが効く**（`accumulateVtolControl`）。舵は風が当たらないと
  効かないので、リフトエンジンだけで真上に上がる機体は尾翼が「進んでいる向き」へ
  機首を向けようとして、そのまま引っくり返る。実機（ハリアーやF-35B）はエンジンの空気を
  機首・尾部・翼端のノズルへ回してこれを押さえている。ここでも同じものを持たせ、
  リフトの出力に比例して効かせ、舵から手を離しているあいだは水平へ戻す。
  - ノズルを消すタイミングは**総速度ではなく機首方向の速度**（`state.forwardAirspeed`）で
    決める（60m/sまで）。総速度で決めると、まっすぐ上へ加速しているだけの機体
    （機首方向の速度は0）が一瞬で基準を超えてノズルを失い、水平飛行用に向いた
    水平尾翼が真上からの風を受けて暴れるだけの状態に取り残される。
  - ただし**ノズルの力には限りがある**。水平尾翼は水平飛行でよく効くよう
    面積を大きく・重心から遠くに置くので、真上からの風（迎角ほぼ90°）に対しては
    その面積と腕の長さがそのまま桁違いの抗力モーメントに化ける。位置と推力の
    釣り合いが完璧でも、上がる速さそのものがノズルの持ち分を超えれば機体は回る。
    `vtolClimbSpeedLimit` が実際の空力計算（`accumulateAeroForces`）そのものを使って
    「姿勢は水平のまま、真上への速度をどこまで上げるとモーメントがノズルの持ち分を
    超えるか」を挟み撃ちで求め、機体がその速度を下回るように性能診断へ警告を出す。
    エンジンの推力は姿勢に効かない（釣り合っていれば）ので、この限界はスロットルに
    関係なく機体の形だけで決まる——垂直レバーをゆっくり操作するか、水平尾翼を
    小さく・重心に近づけるまでは、慎重に上がるしかない。
- **垂直離陸用エンジンの前後バランスは自動で取る**（`applyVtolTrim`）。重心の前後どちらかへ
  寄って置いた分だけ、そのエンジンはレバーを開けただけで機首を振る力になる——左右対称は
  ミラー複製で簡単でも、前後をぴったり重心に合わせるのは難しい。実機（F-35Bなど）が前後の
  ノズルの配分を変えて消しているのと同じことをする：前群・後群のモーメント（推力×腕）を
  比べ、小さいほうを基準にもう片方を絞って、レバーをどれだけ開いても機首を振らないように
  する。絞った分だけ定格より使える推力は減るので、`vtolThrustN`（実際に使える合計）と
  `vtolThrustNRaw`（絞る前の定格）の両方を持たせ、性能診断に「定格の何%まで」と出す。
  位置をぴったり合わせなくても飛べるようになる代わりに、離れているほど使える推力は減る。
- **地面の高さは `terrainSurfaceHeightAt`**（実際に描かれている面）を読む。真の高さ関数
  `worldHeightAt` を使うと、遠くのLODが粗いところで車輪が地面にめり込む。
- 物理は1/240秒の固定刻みで回す（接地のばねが硬いため）。描画ループのdtが0.1秒で
  頭打ちなので、そこまで追いつけるだけのサブステップを持たせている。ここが足りないと
  **描画が重い環境で機体だけスローモーションになる**。
- 風は天候から受け取る（`EnvState.env.windSpeedKmh` / `windDirectionDeg`）。高度が上がる
  ほど強くする。滑走路に出すときは向かい風になる側の端を選ぶ。
- **墜落判定（`js/env/12-flight-mode.js`、`FLIGHT_CRASH_G=12`）は `state.loadFactor`
  （機体の上下方向のG。HUDの「G」計器と同じ）で見る**。以前は接地中の速度ベクトル
  全体の変化量で見ていて、これだと推力そのものの加速度まで拾ってしまい、
  推力/重量比が18倍を超える超音速機がフルパワーで滑走を始めただけで
  （こけていないのに）「墜落」になっていた。loadFactor は機体の上下成分だけを見るので、
  ほぼ真後ろ向きの推力はここに出てこず、接地の衝撃（車輪のばねが縮む向き＝上下）は
  ちゃんと拾える——沈下率の直接チェック（`FLIGHT_CRASH_SINK_MPS=9`）と合わせて2本立て。
- **トリム（舵の中立位置）を持つ**（`solveLevelTrim` / `controls.trim`、キーは T・Y/H）。
  重心を主翼の空力中心に合わせると主翼のモーメントが消えるので、釣り合う迎角は
  「水平尾翼の取付角の裏返し」だけで決まる。取付角0°の尾翼なら**揚力の出ない迎角**で
  釣り合ってしまい、手を離した機体は高度と速度を交換しながら延々とうねる
  （内蔵機もTB1もTB2もこれで、ピッチが±30°振れていた）。実機と同じくトリムで解く。
  - トリムは**飛行モデルそのものを使って解く**。「その速度で水平飛行する迎角・トリム・
    スロットル」を挟み撃ちで求める。近似式を別に持つと本体の物理と食い違っていく。
  - 滑走路に出すたびに上昇速度で自動で取っておく。T キー（画面では「トリム」ボタン）で
    いま飛んでいる速度に合わせて取り直せる。Y/H で微調整。
  - 失速角の手前で頭打ちにして探す。**失速しないと重さを支えられない機体は
    「解けなかった」と答えるのが正しい**ので、その場合はトリムを中立のままにして、
    理由（`wing` 翼が足りない／`elevator` 舵角が足りない／`no_elevator` 舵に腕が無い）
    を性能診断に出す。`no_elevator` は**トリムを両端まで振ってもモーメントがほとんど
    変わらないことを直接測って**判定する——水平尾翼を持たずエルロンだけで飛ばす機体
    （デルタ翼のエレボンなど）で重心を主翼の空力中心にぴったり合わせると、主翼をひねっても
    力の掛かる点が重心の真上になり、腕（重心からの距離）が無くなる。優先順位を付けずに
    `!liftOk ? 'wing' : 'elevator'` とだけ書いていたときは、この根本原因が
    「翼が足りない」という無関係な理由に埋もれて出ないままだった
    （エンジン推力が重心から外れて出る一定のピッチモーメントを、効かない舵では
    一生打ち消せず、機首が勝手に振れ続ける機体になっていた）。
- 操縦はキーボード。舵は押している間に中央から育ち、離すとばねで戻る（いきなり最大に
  すると細かい修正ができない）。視点は追尾／コックピット／機体まわり／自由の4つ。
  W/S・↑↓ ピッチ、A/D・←→ ロール、Q/E ラダー、Shift/Ctrl 出力、X/Z 垂直エンジン、
  T トリムを取る、Y/H トリム微調整、B/Space ブレーキ、G 脚、V/C フラップ、
  **O 高度維持、I 全自動**、P 駐機、Tab 視点、R 滑走路へ戻る、F 飛行終了。
- **画面の上の操縦装置**（`js/env/11b-flight-touch.js`）。スマホには Shift も Tab も無いので、
  指で触れるレバー・ボタンを画面に重ねる。タッチ画面では自動で出て、
  右パネルのチェックで切り替えられる（その選択は保存される）。
  - **エレベーター（昇降舵）とエルロン（補助翼）は別々のレバー**——縦のレバーがピッチ、
    横のレバーがロール。1本のスティックにまとめると、片方だけを微妙に動かしたいときに
    反対側も一緒に動いてしまうので、指で細かく操作するにはそれぞれ別に触れたほうがいい。
    どちらも中央から帯が伸びる表示で、伸びた向きと長さで舵の向きと大きさが分かる。
  - エレベーター・エルロンは離すと中央へ戻る。出力レバー（スロットル・垂直用）は離しても
    位置が残る——実機のスロットルと同じで、指を離すたびに全閉になったら離陸もできない。
  - 出力レバーは `controls.throttle` を直接書く。キーボードは「毎秒どれだけ動かすか」を
    足し込む作りなので、どちらを触っても同じ値が動き、取り合いにならない。
  - pointer イベントを1本ずつ `setPointerCapture` で捕まえる。こうしないと
    「エレベーターを握ったままエルロンも操作する」ができない。
  - ボタンはキーボードと同じ `handleFlightKeyPress` を通す。処理が2か所に分かれると
    必ず片方だけ直し忘れる。
- 機体は Builder の IndexedDB（`flightSimDB`）から直接読む。同じオリジンなので
  保存し直さなくてよい。Builderで何も作っていなければ**内蔵の練習機**で飛べる。
  内蔵機もBuilderと同じ書式の定義なので、飛行モデルの作りかたは1本で済む。
- **重心は飛行画面からも前後・上下・左右に動かせる**。Builderで決めた値からの「ずれ」として
  持つので、0に戻せば必ず設計どおりに戻る（設計はBuilder側が正、こちらは積み方を変えるぶん）。
  動かすと静安定・車輪までの距離・診断がその場で変わる。スライダーの目盛は機体の広がりに
  比例させてあるので、10mの機体でも100mの機体でも同じ操作感になる。
  **見た目は作り直さない**——GLBの読み直しは重く、スライダーを動かすたびに固まってしまうので、
  飛行モデルだけを組み直し、見た目は「重心ぶん戻す」位置をずらすだけにしている。
- **その機体が飛べるかを診断する**（`analyzeAircraftPerformance`）。Builderは機体が成立して
  いるかを何も教えてくれないので、翼面荷重・失速速度・離陸滑走距離・静安定・
  「地上で機首を上げられるか」を出して、引っかかっている点を右パネルに名指しで並べる。
  滑走路の端まで走っても浮かない、の原因が推力なのか翼面積なのか尾翼の位置なのかは、
  飛ばしてみても分からない。勝手に機首が上がる／下がる機体もここで分かる：
  - 主翼の揚力が重心の前後にずれている（翼弦の15%以上）
  - エンジンが重心を通っていない（スロットルを開けるほど機首が振れる）
  - トリムを一杯まで取っても水平飛行に釣り合わない（舵が足りないのか翼が足りないのか）
  - 車輪が重心を前後で挟んでいない（置いただけで尻もちをつく／機首から突っ込む）
  - 車輪が左右のどちらかに寄っている（ミラー複製でX位置が反転していない）
  - 静安定が60%MACを超えている（水平尾翼が大きすぎて迎角が0°に固定され、舵で機首が上がらない）
- **自動操縦**（`js/env/13-autopilot.js`、キーは O と I）。「設定した高度を飛び続ける」だけの
  高度維持と、出発の空港から目的地の空港まで通しでやる全自動の2段階。
  作りは4段の入れ子で、外側ほどゆっくりした量を決め、内側が舵を動かす：

      高度のずれ → 昇降率 → ピッチ角 → エレベーター
      方位のずれ → バンク角          → エルロン
      速度のずれ →                    → スロットル

  - **符号は実測して決める**。`controls.roll` を+にすると `rollDeg` は増えるが
    `angularVelocity.z` は**減る**（ピッチとヨーは同符号）。ロールの減衰項だけ足し算になる。
    ここを取り違えると発散するので、機体を実際に飛ばして測った。
  - **エレベーターは比例だけでは足りない**。フラップを下ろす・脚を出す・速度が変わると
    釣り合う舵の位置が動くので、比例項はずれを残したまま止まる（実際、進入でフラップを
    全開にした途端に降下が止まり、401mの高さで滑走路へ向かって水平飛行した）。
    残った舵をゆっくり `controls.trim` へ移して積分項にしている——人間がトリムを
    取り直すのと同じことを機械にやらせる形で、解除したあともトリムが残る。
  - **昇降率の上限は経路角で決める（推力からではない）**。降りるのに推力は要らないので、
    推力/重量で上限を決めると重い機体の降下が頭打ちになり、3°の進入線に一生乗れない
    （大型機が滑走路を素通りした）。同じ角度なら速い機体ほど昇降率が大きいのが正しい。
  - **坂を追うときは、その坂が要求する降下率を先に足す**（前送り）。高度のずれ×比例だけだと
    降下率を出すためにずれが残り続けるしかなく、進入線から数十m浮いたまま飛ぶ
    （比例ゲイン0.1なら、5.8m/s降りるのに58mの浮きが要る）。
  - **横方向は方位ではなく航跡（地面に対して進んでいる向き）で見る**。機首を滑走路に
    合わせるだけでは横風でそのまま流されるが、航跡のずれで舵を切れば必要なぶんだけ
    勝手に機首が風上へ向く。40km/hの横風で中心線から220mずれていたのが15mになった。
    機首を滑走路と揃えるのは引き起こしにかかる高さから——早く揃えるとそのぶん流される。
  - **上昇は速度の余裕ぶんだけ**。高度を追いかけて速度を使い切るのが自動操縦のいちばん
    危ない壊れ方で、高度維持を入れたまま出力を絞ると失速速度の下でぶら下がったまま飛ぶ
    （練習機が失速速度以下の27m/sで200秒飛んだ）。余裕が無ければ高度をあきらめる。
  - 段階は `takeoff → climb → cruise → descent → approach → flare → rollout`。
    切り替えは**高度・距離・接地だけ**で決め、時間では決めない（機体によって加速も
    上昇率も違う）。進入端の手前9kmに最終進入開始点を置き、そこから3°で降りる。
  - **引き起こしは滑走路の近くにいることも条件にする**。対地高度だけで決めると、
    何km も手前で盛り上がった山の上を通っただけで引き起こしに入ってしまう。
  - **沈下率は残りの高さに比例させる**。一定の沈下率にすると速い機体ほど長く浮き、
    滑走路を使い切る（大型機が2.7km先で接地した）。高いうちは速く、近づくほどゆっくり。
  - **降りられなければやり直す**（`goaround`）。滑走路の半ばを過ぎてもまだ浮いていたら、
    最終進入開始点の高度まで上げてそこへ戻り、もう一度進入に入る。ここで諦めないと
    滑走路を素通りしたまま永遠に飛び続ける。
  - 目的地は右パネルのセレクトで選ぶ（出発はいま選んでいる空港）。選び終わりに
    **焦点を外す**——セレクトに焦点が残っていると、そのまま I を押しても
    「入力欄で打っている」と見なされて効かない。
  - 高度維持だけのときは**ピッチとロールしか持たない**。出力と方位は手のまま操れる。
  - **巡航はできるだけ速く飛ぶ——ただし旋回できる速さまで**。目標速度を最高速度の
    97%に置くだけで、あとはスロットルが勝手に全開へ張り付く——ぴったり最高速度を
    狙うと、推力と抵抗が釣り合ったところを永遠にスロットルで追いかけることに
    なるだけなので、97%で十分（そこにも届かなければ、出力は全開のまま自然に
    頭打ちで安定する）。**ただし最高速度をそのまま使うと、フィクションの
    超音速機（最高速度にマッハ21のような桁外れな値が入ることがある）で
    旋回できなくなる**——旋回半径は `v²/(g·tanθ)` で速度の2乗に効くので、
    秒速数kmまで加速すると、バンク角を目一杯使っても半径が数千kmになり、
    事実上まっすぐにしか飛べない（手動操縦はできるのに自動操縦だけ目的地へ
    向き直せず、素通りし続ける、という報告になった）。なので巡航速度には
    「その速さ・その旋回半径の上限（40km）でその機体のバンク角上限まで
    傾けた旋回ができる速さ」という上限（`apSpeedSchedule` の `turnableV`）も
    掛けておく——「できるだけ速く」を「実際に着ける速さで」に直したかたち。
  - **バンク角の上限（`apBankMaxFor`）は、機体の最高速度が上がるほど引き上げる**。
    25°は民間機の常用域（乗客がいる想定でゆったり曲がる角度）で、遅い機体
    （194kt以下）はそのまま使う。実機の戦闘機はもっと深く傾けて旋回半径を詰めて
    おり（`tanθ`が効くので25°→60°で半径は1/3強）、速い機体ほど深いバンクを
    許すことで旋回半径そのものを縮め、`turnableV`（＝巡航で出していい速さ）を
    底上げする——マッハ2（680m/s）あたりの機体は60°に達し、それ以上速い機体も
    60°で頭打ち（実機の常用域を外れる深さまでは傾けない）。ふつうの機体
    （最高速度が194kt程度まで）はこの変更の影響を受けず、以前と同じ25°・
    最高速度の97%まで出る。
  - **旋回半径は「世界の大きさ」だけでなく「いま飛んでいるルートの長さ」にも
    合わせて絞る（`apCruiseTurnRadiusMax`）**。上のバンク角の変更だけでは、
    目的地までの距離が旋回半径（世界基準で40km）より短い実際の経路
    （サンダーバード1号のような推力/重量20倍超の機体を実データで飛ばして
    見つかった）で、旋回そのものに使う弧の長さが目的地までの距離を超えてしまい、
    旋回できないまま目的地の周りを永遠に回り続けていた（旋回できず、
    巡航中フラフラする、という報告になった）。目的地までの距離の1/6
    （最短3km）まで旋回半径を絞ることで、旋回に使う弧の長さがルートの長さに
    対して無理のない範囲に収まるようにした。
  - **上昇中、出力が全開のままなのは推力が普通の機体まで**。上昇は姿勢
    （最大15°）だけで速度を頭打ちにする設計だが、推力/重量比が実機の何倍もある
    フィクションの超音速機は、姿勢を目一杯まで上げても抗力が追いつかず、
    速度が青天井に伸び続けて上昇中に目的地をはるかに通り過ぎてしまう
    （旋回半径は速度の2乗で効くので、曲がれる速さを大きく超えたまま飛ぶと
    そのぶん旋回に距離を食う）。曲がれる速さの1.5倍を超えたら、そこだけ
    出力を絞るようにした——ふつうの機体はこの閾値に達しないので影響を受けない。
- **数字は `node tools/verify-flight.js` で確かめる**。離陸滑走・上昇率・失速速度・
  旋回のG・着陸・向かい風の効果まで、ブラウザを開かずに測れる
  （THREE.jsは数学しか使っていないので、ブラウザ用のファイルをそのままNodeで読める）。
  内蔵機はいま 離陸滑走308m／上昇567fpm／失速60kt（フラップ全開50kt）／
  30°バンクで1.15G（理論値1.155）。
  自動操縦は**滑走路に置いて、着陸して止まるまでを丸ごと回して**確かめる——
  進む向きを4通り（旋回なし／45°／180°／90°横の滑走路）、横風あり、
  高すぎる進入からのやり直し、寸法4倍・重量150倍の大型機まで。
  中心線からのずれ・接地の衝撃・沈下率を毎回測っているので、
  ゲインを触れば降り方が悪くなったことがすぐ分かる。

### 深度バッファ（ハマりどころ）
- カメラは near=1 / far=260km。**通常の深度バッファでは数十km先で数十mの高低差が潰れ**、
  海面(y=0)が標高10mの島や滑走路を手前に描いてしまう。そこで対数深度バッファ
  （`logarithmicDepthBuffer: true`）を使っている。
- ただし **three.js r128はWebGL2だと `EXT_frag_depth` が無い扱いになり、
  深度を頂点で計算して画面上で線形補間する経路に落ちる**。logは上に凸なので、
  1枚のポリゴンが手前から奥まで大きく伸びていると、補間された深度が本来より手前に寄る。
- したがって **巨大な板を1枚のポリゴンで作ってはいけない**。
  海面は「カメラ中心の同心円メッシュ（近いほど細かい）」にしてある。
- 霧の濃さも視程に合わせること。数km用の濃さのままだと、数十km先の山も海も
  一様な白い壁になる。現在は 0.0000105（80km先でおよそ半分霞む）。

### 都市と地名ラベル
- 都市は `WORLD_CITIES` から手続き的に生成する。建物の配置は **都市IDから作った
  決定論的な擬似乱数** で決めるので、何度読み込んでも同じ街並みになる。
- 1都市の建物を1メッシュに、夜景の灯りを1つのPointsにまとめている。
- 地名ラベル（国・山脈・都市・空港コード・川・湖）は種類ごとに見え方を変える。
  国名は遠くからでも読めるようにフェードを緩めてある。
  **画面上で一定の大きさになるよう毎フレームスケールを計算する。**

### ミニマップ
- 世界／広域（700km）／周辺（160km）の3段ズーム。
- 焼き付けは1枚あたり5万点以上のサンプルになるので、数行ずつフレームをまたいで進める
  （一気にやると視点移動のたびに固まる）。「世界」の1枚はキャッシュする。
- 北西からの陰影を足してあるので、地図でも山脈の走り方が分かる。
- クリックするとその地点へ視点が飛ぶ。3,000km四方を3Dビューだけで移動するのは無理なので、
  マップ上の移動手段も兼ねている。

### 空港
- `WORLD_AIRPORTS` の空港をマップ上の **固定の位置・標高・方位** に建てる。
  外部モデル(GLB)の読込には未対応。
- 空港の設定（滑走路の長さ・幅・方位・灯火・表示）は **空港IDごとに `EnvState.airportSettings`
  に持つ**。建っていない空港の設定も残るので、圏外へ出て戻っても失われない。
  これがそのまま保存/読込の対象になる。
- 空港はローカル座標で「滑走路の長さ方向 = +X、幅方向 = Z」に組み立て、
  グループごとワールド上の (x, 標高, z) に置く。
  **方位はグループ全体の `rotation.y` だけで表す**。ワールドは -Z が北・+X が東で、
  方位θの向きは (sinθ, 0, -cosθ) なので `rotation.y = 90° - θ` になる。
- 滑走路の呼称は方位から算出する（90°→「09/27」。0°は"00"ではなく"36"）。
  端の数字は着陸してくる側から読める向きに置く必要があるため、
  面内で90°回してから寝かせている（Euler 'XYZ' は Z→Y→X の順に効く）。
- 路面標識は小さな長方形を1つのBufferGeometryにまとめて1メッシュにしている。
  **頂点は「上から見て反時計回り」に積むこと。** 逆にすると裏面扱いになり、
  MeshLambertMaterialは裏面を法線反転で照らすため標識が真っ黒になる。
- 地形は空港の標高へ完全に均される。**UIで滑走路を伸ばせる上限（+900m）ぶんの
  平地をあらかじめ確保してある**ので、伸ばしても斜面にはみ出さない。
- 灯火は頂点カラー付きの1つのPointsにまとめ、昼夜サイクルの `dayFactor` から
  不透明度を決める（自動／常時点灯／消灯を選べる）。
- 吹き流しは風向へ向き、風速で垂れ角が変わる（30km/hで水平）。

### 設定の保存と読み込み
- 保存するのは **マップの定義からの変更ぶんだけ**。地形・国・都市・空港の位置は
  種から決まる固定のものなので保存しない。
- 触るたびに localStorage へ自動保存し、次に開いたとき復元する。
  `.json` の書き出し／読み込みもできる（端末をまたいで持ち運ぶ用）。
- 保存データには **世界の種と一辺** を書いておく。世界の定義を変えると
  保存データは意味を失うので、読み込み時に食い違いを知らせ、
  今の世界に無い空港IDは読み飛ばす。
- 読み込んだ値は範囲で丸める（例：滑走路の長さは均してある平地に収まる範囲へ）。
  壊れたファイルを読ませてもシーンは壊れない。

### バージョン管理
- `js/01-state.js` の `APP_VERSION`（Builder）、`js/env/01-env-state.js` の
  `ENV_VERSION`（環境プレビュー）がそれぞれの版数。画面左下に表示される。
- 配布時はZIPのファイル名・フォルダ名にも同じ版数を入れる（`flight-sim-v13.zip`）。

### 保存データ
- IndexedDB（`flightSimDB`）に、3Dモデルのバイナリ込みで保存。
- 設定ファイル(.json)のエクスポートは **3Dモデルを含まない**（デバイス間で持ち運ぶ用）。
- 旧バージョンのデータとの互換性は `rebuildPartsFromSaved` と
  `applyConfigDataToCurrentModel` 内でフォールバックを入れて吸収している。
- 環境プレビューの設定（時刻・雲量・風・空港の変更）は localStorage に自動保存され、
  `.json` で書き出し／読み込みもできる（`js/env/08-env-storage.js`）。
  Builder側のIndexedDBとは別物で、互いに影響しない。

## 実装済み機能

### Builder（`index.html`）
- GLB/GLTF読込（D&D対応）、最後に開いた設定の自動復元
- パーツ配置：エンジン / 翼・尾翼 / 可動翼面 / 航行灯 / 着陸脚
- 重心（CG）の表示・調整、主翼の空力中心（前縁から1/4翼弦）からの自動算出（X・Y・Zとも）
- 垂直離着陸用エンジンの釣り合い表示と、推力を解いて重心の真上へ揃える
- ピッチの釣り合い表示（静安定・エンジン推力のずれ）と、重心の位置＋エンジンの角度を
  解いて一発で整える「空力バランスを整える」
- エンジン出力の自動設定：設定した最高速度・垂直離陸それぞれに必要な推力を逆算、
  通常／垂直エンジンをまとめて倍率で増減する一括調整
- 翼の4頂点編集（ギズモ＋数値入力）、揚力中心の自動計算
- 可動翼面を翼の後縁1/4へ自動配置、翼側から一発で追加
- 着陸脚の関節・伸縮節の追加/削除、展開/格納テスト、地面への自動フィット
- 左右対称ミラー配置（頂点・取付位置も反転）
- 機体全体の向き・大きさ・重量・最高速度（ノット/マッハ）
- 原点調整（軸を選んで中心合わせ）
- 透視投影 / 平行投影の切替、前後左右上下の軸ビュー
- モバイル対応（ドロワー式パネル、横スクロールするツールバー）
- 設定のダウンロード / インポート

### 環境プレビュー（`flight.html`）
- **世界**：3,000km四方の固定マップ。陸と海、標高（平地〜約3,800mの山脈）、
  気候帯（緯度・内陸度・標高から気温と乾燥度を出し、森林限界・雪線・地表色に反映）
- **国と地名**：10の国・130の都市・78の空港・10の山脈。地名は国ごとの音節表から生成
- **川と湖**：山地から海まで流れる川68本、湖50。どちらも地形そのものに谷と窪地として刻む
- **植生**：気候から密度と色が決まる樹木（手前1.2km・低空のみ）
- **空**：大気散乱シェーダー・太陽/月/星、昼夜サイクル（周期調整可、デフォルト15分）、
  積雲（風速・風向で流れる）、高度による空の色・霧のプレビュー
- **天候**：場所と時間で移り変わる（3,000km飛べば天気も変わる）。
  快晴／晴れ／曇り／雨／雷雨／雪／霧のプリセットと、湿り・荒れ・霧を自分で決める手動モード。
  曇り空の天井、雨と雪の降水、視程に連動した霧、雷、突風、天候に追従する風速
- **空港**：滑走路（長さ・幅・方位を調整可、呼称は方位から自動算出）、
  路面標識（センターライン・末端の縞・接地帯・目標点・端の数字）、誘導路・エプロン・管制塔、
  灯火（夜間に自動点灯／常時点灯／消灯）、風に追従する吹き流し。
  山岳空港や島の空港も同じ仕組みで成立する
- **ナビゲーション**：2D世界地図（3段ズーム・クリックで移動）、気象レーダーの重ね表示、地名ラベル、
  現在地・地表の標高・最寄りの空港の表示、国ごとにまとめた空港の選択
- **飛行**：Builderで作った機体（またはBuilder未使用でも内蔵の練習機）を選んだ空港の滑走路に出し、
  実際に離陸・飛行・着陸できる。翼ごとの空力による飛行物理（失速・スピン・上反角効果・
  舵の減衰まで挙動として出る）、天候の風と乱れ、キーボード操縦と**画面の上の操縦装置**
  （スマホでも飛ばせる）、垂直離陸用エンジンの独立したレバーと姿勢制御ノズル、
  追尾／コックピット／機体まわり／自由の4視点、対気速度・高度・方位・昇降・出力・
  フラップ・トリム・脚・迎角・G・対地高度の計器と失速警告
- **自動操縦**：設定した高度を飛び続ける高度維持（O）と、目的地の空港を選べば
  離陸・上昇・巡航・降下・進入・着陸まで通しでやる全自動（I）。降りられなければやり直す。
  巡航は最高速度のすぐ下まで加速する（できるだけ速く着く）
- **保存**：時刻・天候・風・空港の変更・飛行の機体と視点と重心の調整を localStorage に自動保存、`.json` で書き出し／読み込み

## 既知の注意点

### Builder
- パーツの位置は機体モデル基準の相対座標なので、**別のモデルに設定ファイルを適用すると位置がずれる**。
- 原点調整は **モデル本体だけ** を動かす。パーツ配置後に使うと相対位置がずれるため、
  モデル読込直後に使うのが前提（UIでも確認ダイアログを出している）。

### 環境プレビュー
- **地形のパラメータを触ったら必ず `node tools/verify-world.js` を流すこと。**
  街が海に沈む・滑走路が斜面に乗る・川が海に届かなくなる、といった壊れ方は
  見た目では気付きにくい場所で静かに起きる。
- **巨大な板を1枚のポリゴンで作らないこと**（「深度バッファ」の節を参照）。
  海面が陸地を覆い隠すという分かりにくい壊れ方をする。
- **地面に載せるものは `terrainSurfaceHeightAt()` を使うこと**（「地形メッシュの上の高さ」の節）。
  `worldHeightAt()` の値に置くと宙に浮く。
- 地名ラベルは `depthTest: false` で描いているので、山の裏側にある街の名前も透けて見える。
  ナビゲーション用の地図的な見え方を優先した結果で、意図した挙動。
- 木は手前1.2kmにしか出ない。その外との境目は、低空で横を向いているときに
  わずかに見えることがある（上空では消えるので目立たない）。
- 国境線は引いていない。国の範囲は「もっとも近い都市の国」という簡易判定
  （`worldRegionAt()`）で、現在地表示にだけ使っている。
- 空港の位置・標高・滑走路の向きはマップの一部なのでUIからは変えられない。
  変えるときは `js/env/03b-world.js` の生成規則を直す（地形の均しも追従する）。
- `EnvState.env.windDirectionDeg` は **「風が流れていく向き」** として扱っている
  （雲の移動方向、吹き流しの向き、海面のうねりがこれに従う）。航空の慣習である
  「風が吹いてくる方位」とは逆なので、風向を航空式に合わせるなら符号を反転する必要がある。
- 太陽位置・季節は簡易的な正弦モデルであり、実在の緯度・経度・日付に基づく
  天文計算ではない（ゲーム的に「それらしく」見えることを優先している）。

### 共通
- Three.js r128を使っているため、`Quaternion.invert()` のような新しめのAPIは避け、
  自前計算に置き換えている箇所がある（バージョン差異でハマった経緯があるため）。
